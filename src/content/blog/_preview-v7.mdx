I built a benchmark that evaluates ID Capture over distorted audio channels. The benchmark caught a regression in my voice agent when I swapped in a bigger speech-to-text (ASR) model. This led me to investigate the shortcomings of using ASR transcription confidence as a proxy for whether the model heard correctly.

## The question

Voice agents are being deployed in increasingly high-stakes scenarios. We're still in the early phases of the rollout. Today, a critical failure often means lost revenues. But a future where we rely on voice agents for safety-critical roles means that effective evaluation becomes essential for health and safety.

Imagine a medical scribe agent capturing the wrong medication name, an emergency dispatch agent capturing the wrong street address, or an air traffic control agent hearing the wrong flight number. These errors can result in harm to humans.

The examples above are all instances of the critical failure mode of mishearing key information. When the agent can't reliably hear, it shoule *escalate to a human*. So the practical question, for anyone building one of these agents, is: how does it know?

### The trouble with ASR Confidence

Most ASR models expose some kind of confidence number. The Whisper family of models, for example, exposes the per-token probabilities of the transcript it decoded. A natural way to represent its overall confidence in its transcription then is `exp(avg_logprob)`, the geometric mean of the per-token probabilities.[^2] You can then wire that into an escalation policy: above some threshold, commit; below another, escalate; in between, ask the person to repeat.

But ASR confidence isn't the same as correctness. It scores how confidently Whisper produced *the tokens it chose*, not whether those tokens are *true*. In some scenarios confidence is a good proxy for correctness. On clean-ish audio a dip in confidence might correspond to a mistaken letter. But on degraded audio ASR confidence decorrelates from correctness. And the agent can't tell from ASR confidence which regime it's in. For example, when given severely degraded audio, Whisper often hallucinates a transcription with high confidence (see the top image). So is the model confident because it hallucinated on degraded audio or because it's actually correct? 

We'll look at how Whisper behaves on my ID capture benchmark to get a sense for the failure modes of ASR confidence as a predictor of speech-to-text transcription correctness. 

## The benchmark

<AgentFlowDemo />

The benchmark simulates the challenge of capturing essential info over degraded audio channels. I generated 100 test cases (200 audio fixtures total, two attempts per case) using the ElevenLabs TTS API. Each fixture is a short spoken identifier, e.g. *"S as in sierra, X-ray, one, one, eight, five"* (so the canonical ground truth here would be: `SX1185`). The cases span five buckets of increasingly degraded audio. The tricky part of the benchmark is that fixtures in the 'severe' bucket are designed to be unrecoverable. These adversarial examples exist to check that the agent escalates when needed.

| Bucket | n | Distortion |
| --- | --- | --- |
| clean | 15 | none |
| light | 15 | mild noise OR phone bandpass alone |
| moderate | 20 | phone bandpass + 10 dB SNR noise |
| heavy | 25 | phone bandpass + 5 dB SNR + light dropout |
| severe | 25 | phone bandpass + −12 dB SNR + 250 ms dropout @ 55% per-window |

### Simulating phone distortion
The deterministic degradation pipeline simulates the sort of distortion artifacts that you hear on a phone call (you might say it's a bit phone-y[^1]): a 300–3400 Hz bandpass (the standard phone band), a μ-law codec roundtrip (the standard phone codec), additive white noise at a configurable SNR, and packet dropout where 250 ms windows are silenced at a configurable probability. The severe bucket layers all four and pushes things beyond human-level recoverability. Also, the catalog is seeded, so rerunning the generator produces byte-identical fixtures.

### The agent loop
For each case, the agent being tested receives the audio file and chooses one of three actions: commit a transcription, ask the other person to repeat (one retry allowed), or escalate to a human. To recap, on the cases where the audio is actually unintelligible, the right behavior is to escalate. If your agent is recording something like a medication, an emergency address, or a patient identifier, you want it to fail loudly. The benchmark then grades the agent on % accuracy as well as escalation precision/recall (i.e. to what extent did it escalate on impossible cases but not on tractable cases?).

To exercise the benchmark I built a simple deterministic agent that wraps a Whisper ASR model.[^4] The agent transcribes the audio, runs a deliberately simple parser over the transcript, and decides whether to escalate based on Whisper's confidence. My agent's austere escalation policy looks like this:

```python
# voice_agent_eval/whisper_agent.py — the policy gate

def decide(asr_text: str, confidence: float) -> Action:
    parsed = parse_id_shape(asr_text)   # uppercase, strip, normalize

    if parsed is None or confidence < ESCALATE_BELOW:
        return Escalate()
    if confidence < CONFIRM_BELOW:
        return AskForRepeat()
    return Commit(parsed)
```
### Simplifying Assumptions Focus The Benchmark
What we're doing here is taking a surgical approach to checking a single domain-specific high-stakes failure mode. By discarding extraneous details we're able to better isolate what we're interested in.

Some of the complexities this setup removes:

- Both the benchmark's interlocutor and the agent I built to exercise the benchmark forego an actual LLM for the 'brain' of the agent. They're fully deterministic. Only the ASR model introduces uncertainty.
- We also forego any sequence of realistic conversational turns preceding the ID transcription challenge.
- The benchmark provides the agent very limited options: submit a transcript capture, escalate to a human, or ask to repeat the audio file.
- Importantly, the setup completely ignores many of the essential challenges of the voice agent domain: turn-taking, barge-ins, end-pointing, latency, etc. In fact, the benchmark is *not* even real-time. It's turn-based, with an optional HTTP-based FastAPI server. These real-time issues are not germane to the question our benchmark is asking.

It's also worth pointing out that the purpose of this benchmark is not to assess frontier capabilities, but rather to catch regressions. The current generation of agents can easily perform well on it already.

## The regression

I ran my agent on the benchmark with four different Whisper ASR model sizes. When I initially swapped them in without tuning the escalation policy threshold, accuracy increased monotonically while wrong-commit rates on the ~impossible 'severe' bucket tasks rose from 0% in tiny.en up to 64% in large-v3 😬.

### All the ways you could have missed this regression
Let's walk through the layers of how you might miss it in practice:

1. **Having an agent that has no way of knowing how confident it is in its transcription** (from my personal conversations, this seems to remain common as of this writing). In this case it's a moot point and you'll find out from your customers.
2. **Not specifically evaluating the failure mode you're interested in.** If it would be really bad for your voice agent to fail in production by mishearing certain info and not escalating, then your eval suite should test for that. It would be easy to gloss over in a broad end-to-end evaluation.
3. **Only looking at ID capture accuracy.** "Look! Accuracy increases with a bigger model." Ignoring the escalation behavior would miss the bug.
4. **Not including adversarial examples in the benchmark** If you only tested clean samples you also would miss it.
5. **Only looking at the aggregate wrong-commit rate.** Check out the amber line in the chart above. Overall the escalation behavior doesn't look so bad. But when you look specifically at the impossible cases, it's clear that the large model has *totally lost the plot*.
6. **Calibrating the model's escalation policy to this benchmark.** The distribution of severe audio samples is arbitrary and has no relation to any actual production situation. Below I do an F1 sweep to find the 'optimal' for each model. But the calibration settings only work for this distribution of fixtures.

## A closer look at ASR confidence

Threshold recalibration restores the Pareto frontier but it turns out ASR confidence has issues that go a bit deeper than our quick-fix. So before reaching for a better calibration trick, it's worth asking: **what is this number actually measuring, why does its meaning slide around, and where does it fall short?**

### What does ASR confidence mean, really?
Whisper is an autoregressive encoder–decoder Transformer. The encoder turns the audio's log-mel spectrogram into a latent sequence. The decoder is a language model that emits text tokens one at a time, each conditioned on (a) the audio, via cross-attention, and (b) the tokens it's already emitted, via causal self-attention. At every step it produces a softmax over the entire ~51.9k-token byte-pair-encoded vocabulary and picks one. So it's really next-token prediction, like an LLM, except the difference from a text-only LLM is the extra cross-attention into the audio.

And `exp(avg_logprob)` is *literally* the geometric mean of those per-step probabilities: `avg_logprob` is the mean of `log P(chosen token)` over the emitted tokens, so `exp(avg_logprob)` is the typical probability the decoder assigned to each word it committed to. Another way of putting this is it's just **inverse perplexity**, where perplexity is `exp(−avg_logprob)`, the standard measure of how surprised a language model is by a string. So high confidence means the model concentrated mass on what it emitted at each step (decisive) and low confidence means it spread its bets. It measures *decisiveness*, not just fidelity to the audio.[^6]

To make sure we're clear on the setup here the following is the classic sequence-of-next-token-predictions pic you've seen from LLM explainers. But here it's whisper-tiny.en decoding a spoken ID one token at a time on clean audio (top) and on severe audio (bottom). Each panel is the model's probability distribution over the *next* token, top five candidates. The colored bar is the token it actually committed.[^5]

On the clean line the distribution collapses onto one token at every step — `R → as → in → Romeo → …`, each a near-certain spike, which is exactly what a confidence near 1.0 looks like up close. On the severe line the same model is guessing: the very first token splits its mass across `You / Welcome / Oh / This / you`, nothing above a few percent. But watch what happens after it commits to "You": the later steps sharpen right back up ("know what I'm going to…"). My strong hypothesis for what's happening here is that once a fluent English sentence is underway it's easy to continue *as language*, regardless of whether it matches the audio. The confidence partially recovers, but on a hallucination.

So indeed to recap, `exp(avg_logprob)` measures how sure the decoder was about the tokens it emitted, not whether those tokens are correct. To get a sense for how those two things drift apart we need to measure the correctness of the model's token predictions more granularly. 

### Character Error Rate as a proxy for per-token correctness

To ask whether confidence tracks correctness, I need the *other* axis: a single number per transcription for how wrong it actually was, that I can plot against the model's confidence. "Right vs. wrong" ID capture is too blunt because a transcript that drops one digit and one that invents a whole sentence are both "wrong," but they're not the same failure. What we intuitively want of course is something like the overall tendency for whether the model's per-token predictions were per-token correct: **Does confidence fall as the wrongness grows?** Character error rate (CER) is a decent starting point.

CER is just edit distance over the length of the reference:

```
CER = levenshtein(reference, transcript) / length(reference)
```

The [Levenshtein](https://en.wikipedia.org/wiki/Levenshtein_distance) (edit) distance is the minimum number of single-character insertions, deletions, or substitutions needed to turn one string into the other. Identical strings score 0; the more the transcript has to be rewritten to match what was said, the higher it climbs. Because the denominator is the *reference* length, a transcript longer than the truth (like a fabricated sentence standing in for a short ID) can score well above 1.0.

Calculating CER requires a bit of thoughtfulness. The *reference you compare against* changes the conclusion completely. My agent's committed value is the post-parser ID string, and if you score *that* against the canonical ID, a wild hallucination collapses to a near-empty string: a one-character slip and a twenty-word fabrication both land at a CER of about 1.0 (because e.g. the string 'a as in alpha' becomes 'a'). The metric saturates where the behavior gets interesting. It can't tell you *how* wrong a confident hallucination is. So instead I score the *raw transcript* against what was actually *spoken* and normalize away formatting that isn't a mishearing.

Here's an example: *"S as in sierra, X-ray, 1, 1, 8, 5"* and Whisper returns *"S is in Sierra, X-ray, 118.5."* Normalized, those become

```
ref: sasinsierraxray1185   (what was spoken)
hyp: sisinsierraxray1185   (what Whisper heard)
```

In this example, there is one needed substitution (the "a" of "as" became the "i" of "is") over a 19-character reference, so CER = 1/19 ≈ **0.05**. Now contrast a severe-audio hallucination. Whisper hallucinates *"Hello, welcome to this channel. Real fast, real fast…"* — which shares almost nothing with what was said, so the edit distance is essentially the entire fabricated sentence and the CER is several times higher (up to ≈4× across this benchmark).[^7]

### Confidence behaves differently on unrecoverable audio

Studying this graph gives an intuition for how ASR confidence behaves differently based on model size and distortion level. Depending on the sort of audio your voice agent has to deal with, this can make ASR confidence an imperfect predictor of correctness, and ultimately, a noisy signal for an escalation classifier. 

If you pool every transcription together, confidence and CER are negatively correlated at about ρ = −0.83 (−0.81 with the abstentions set aside)[^8]. Sounds pretty good. But in practice, not so much. It mostly reflects the fact that clean audio lives in one corner (high confidence, low error) and severe audio in another (low confidence, high error). Pooling the two manufactures a correlation that exists _between_ conditions more than _within_ any one of them. But at inference time you are always inside a single condition.

You can see these two regimes disentangled in the two mini-graphs above. In the non-severe audio graph (right), ASR confidence is a pretty good predictor of correctness. If you inspect the lower confidence dots you see examples where the model had mis-transcribed a few characters but got the general gist of the ID. In the severely distorted cases (left), all models are wrong 100% of the time. Sometimes the model's confidence appears to be propped up by a hallucinated sentence. Other times, it hears a few characters correctly, but mostly misses it. 

Unfortunately the ASR confidence numbers for this unrecoverable regime drift into the confidence region of the graph where we have real signal about clean audio. Consequently, a confidence above 0.55 for recoverable audio means 'probably fine' across all models, but for unrecoverable audio it means a confident mishearing. You can't find a perfect escalation threshold because confidence on moderately distorted overlaps with confidence on unrecoverable audio. 


### Confidence behaves differently for different models
This whole post was kicked off by the observation that larger Whisper models have overall higher confidence, which motivated the threshold recalibration.
The behavior differences between models are more nuanced than simply 'larger models are more confident'.
- The confidence difference is uneven between distortion levels. On clean audio large is much more confident than tiny, while less so for severe audio.
- A hypothesis for the mechanism here might be that larger models hallucinate more confidently. But confidence about hallucinated transcriptions on severe audio is roughly similar across models.
- the real confidence shift in the severe bucket is not on fully hallucinated audio but on extremely garbled audio (ie large-v3's confidence *does* negatively correlate with CER!)
- smaller models abstain more. 
- Bizarrely, Whisper Large does the best on severely distorted audio in terms of both CER and the correlation between CER and confidence. But that ends up just creating more trouble for us if our goal is principally to distinguish between correct vs incorrect. 


### Three things break, all at once

**1. The number stops meaning the same thing.** This is what "threshold drift" really is. It is not that the best cutoff wanders randomly; it's that the entire mapping from confidence to correctness slides as the audio worsens. A confidence of 0.55 means "probably fine" on clean audio and "confident misfire" on severe audio. And you can't correct for the slide, because the variable you'd need to condition on — how degraded this particular call is — is precisely what the bad audio prevents you from knowing.

**2. Right and wrong stop being separable.** On clean audio, correct transcriptions cluster high and the rare wrong one sits lower, so a threshold can split them. As distortion rises the two distributions slide together until they overlap almost entirely. The sharpest way to say it: ask how well confidence can *rank* a correct transcription above a wrong one (its AUROC as a detector). On clean audio it's a decent classifier. By the severe bucket the question is undefined — there are *zero* correct transcriptions, from any model, for confidence to surface. The signal you'd threshold on has nothing left to find.

**3. The model stops admitting defeat.** This is the one that scales with model size, and it's the most consequential. Abstention — returning an empty transcript — is the single fail-safe behavior available on unrecoverable audio. On severe audio, whisper-tiny abstains **58%** of the time; it heard noise and said nothing. Whisper-large abstains **0%** of the time. The biggest model has traded the one move that fails safe for a confident wrong answer, every single time.

You can read all three breakdowns off one operational number. Take a fixed gate — accept any transcript with confidence ≥ 0.55 — and ask how often what it accepts is actually correct. Clean: 90%. Moderate: 79%. Heavy: 62%. Severe: **0%**. The same gate that's a reliable filter on a good line is a rubber stamp on a bad one.

This is also the mechanism behind the regression, in miniature. On the severe bucket, the larger model doesn't just get more accurate on recoverable audio — it pushes *unrecoverable* audio into the region where a candidate exists and the confidence clears the bar:

| Severe bucket | tiny.en | small.en | medium.en | large-v3 |
| --- | ---: | ---: | ---: | ---: |
| Parser produced candidate on first turn | 7/25 | 18/25 | 17/25 | 22/25 |
| First-turn confidence ≥ 0.55 | 0/25 | 2/25 | 4/25 | 12/25 |
| Final wrong commit | 0/25 | 4/25 | 6/25 | 16/25 |

### The whisper-large paradox

Here's a subtlety worth slowing down for, because it looks like a contradiction. Whisper-large is the *most confidently wrong* model on severe audio. And yet, within its own outputs, its confidence is the *best-ordered* of any model: among the things it transcribes, the ones it's more confident about really are less wrong (its within-bucket ρ on severe is −0.54, the strongest of the four). How can it be both the worst-calibrated and the best-ranked?

Because those are two different properties. One is the *offset* — where the whole cloud of confidence sits. The other is the *slope* — whether, inside that cloud, more confidence means less error. A line can sit high and still slope down. Whisper-large does both: it shifts the entire cloud upward (more confident across the board — the headline) *and* tilts it so its internal ranking sharpens.

The catch is that the better ranking is operationally useless, because the whole range has floated above any sane cutoff. Whisper-large's *single most confident* transcription on the severe bucket — the one at the very top of its own scale, at 0.77 — is still a wrong ID. Its confidence does sag on its very worst hallucinations, but every output, top to bottom, sits above the line a clean-tuned threshold would draw. Better relative ranking, worse absolute calibration. The ranking gain buys you nothing when the model saves its highest confidence for fabrications.

One thing the per-model numbers make precise: that upward shift is not uniform. Whisper-large is far more confident than tiny where it has real signal — a median **0.91** on clean audio and **0.82** on its correct hearings, against tiny's 0.67 and 0.63 — but only marginally more confident on severe audio (0.53 vs 0.47). The cloud floated up mostly because the *correct* hearings climbed, and that is what drags the operating threshold up with it (0.55 → 0.75). On the fabrications themselves, large is barely more sure than the small models. So "bigger model, more confident wrong answers" is, more precisely, "bigger model *stops abstaining*, against a confidence scale that floated up on everything it gets right" — not the model believing its hallucinations more loudly.

### What "confidently wrong" actually is

It's tempting to picture the confident errors as the model going rogue and reciting a fluent fabrication. Click the confident-but-wrong dots in the plot above and listen, though, and you mostly hear something more mundane and more alarming: the model confidently *reading back an ID* — just the wrong one. Whisper-large, sure at 0.71, hears `O as in Oscar, 2, 6, 0, F as in Foxtrot, 0, 0` through the noise and returns a crisp, ID-shaped string with letters that were never spoken.

The wrong transcriptions split into two populations that sit at different confidence levels:

- **Garbled read-backs** — still letters and digits, just the wrong ones. Fewer of them (48 of 176 wrong transcripts), but they're the *confident* errors: median confidence **0.56**.
- **Fluent fabrications** — the off-topic "thank you for watching, see you next time" kind everyone pictures. More numerous (128 of 176), but the *least* confident: median **0.44**.

So the dots that clear a confidence gate are overwhelmingly read-backs, not fabrications — and that's the operationally dangerous half. A fabrication doesn't parse as an ID and gets rejected; a confident wrong read-back parses cleanly and commits. The failure that survives to production isn't the model inventing prose where it should have stayed silent — it's the model confidently mis-resolving the identifier it was actually handed.

### Why fluency reads as confidence

Step back and the mechanism is almost obvious. `exp(avg_logprob)` rewards fluent, self-consistent token sequences — that's all a language model's probability really tracks. A bigger model has a stronger language prior, so when the acoustic evidence turns to mush, it has more to fall back on. It doesn't stall; it generates a clean, well-formed, ID-shaped string of digits and letters that it is genuinely "sure" of *as a piece of language* — even though that string has nothing to do with what the caller said.

The confidence isn't a bug in the narrow sense. It's real. It's just confidence in a plausible, wrong ID. The smaller model, with a weaker prior, is more likely to throw up its hands and emit nothing — which is exactly the behavior you wanted. Scaling the model up makes it a better *language* model on degraded input *and strips its instinct to abstain* — and it's the second of those that turns it into a more dangerous *transcriber*.

And the failure mode generalizes. Across the severe and heavy buckets combined, roughly **one in five** transcriptions is *confidently very wrong* — it clears a 0.5 confidence bar while the raw transcript is more wrong than right. Those are precisely the cases a confidence guard exists to catch, and a confidence guard is structurally blind to them. (Not every hallucination is dangerous, to be clear — plenty are low-confidence and get escalated, which is the system working. The dangerous ones are the confident, ID-shaped read-backs — a plausible *wrong* identifier, not lurid prose — and bigger models make more of them.)

## Going beyond ASR confidence (there's a simple fix here)

Firstly, it's clear from the confidence vs CER graph that no amount of threshold calibration is going to produce a perfect classifier. In short, if your voice agent needs to tracnscribe critical info over possibly distorted audio channels, then ASR confidence is probably not a complete solution to inform your escalation policy. This is a good example of a situation where looking at the data really suggests some strong next steps, which might differ from the default approach. 

Namely, a standard tool for classifier calibration is to do something like temperature scaling or isotonic regression, which can turn a raw score into a better-calibrated probability of correctness. One could surely go deep in the technical weeds here but more robust calibration can't ultimately rescue you when the underlying signal lacks further separating power. 

Now take a step back for a second. Are you thinking about the extremely simple (and maybe obvious) major improvement that would resolve most of our wrong commits? **Let your LLM make some common sense decisions!** The LLM will know from the conversation context what sort of value it should expect. If it's expecting to hear a medication name or an ID number etc., and instead hears a hallucinated sentence, then it can reason that there's been a mistake. So boom. That knocks out quite a few wrong commits right there. Additionally, if you look at the data, a number of the most confident wrong commits were actually on the non-severe audio in which the ASR would make contextually apparent mistakes, e.g. transcribing 'U as in Uniform' as 'U.S. in Uniform'. The LLM could catch that as well (though perhaps you'd want to update your system prompt after observing that failure mode). 

Beyond the simple win of just using the LLM as a second layer of common sense quality control, some additional simple improvements are to validate against the real world if that's an option. For example can you check an ID value against a database, and/or are there some formatting or checksum rules it might violate? Thirdly, the LLM can check whether an ID repeated a second time matches what it heard the first time. 

A final consideration is that we need to be mindful of what we're optimizing for. What's your utility function? Probably not F1. We need to optimize the precision/recall tradeoff for the real world context of the task. What is the cost of a wrong commit versus the cost of an extra human review? The escalation threshold needs to reflect the (possibly) asymmetric cost of wrong commits. 

## Reflections

> If you don't know where you are going, you might wind up someplace else.

— Yogi Berra

Whether in life or in evals, it pays to be clear on what you want.

When I built the benchmark, I didn't predict the model-swap miscalibration bug. Indeed if I were building a real agent, the added complexity would surely create opportunities for numerous other bugs. The lesson here is certainly *not* "remember to calibrate parameters when you swap models", nor is it even, "design systems that calibrate themselves so you can set it and forget it". The lesson is that we often can't predict the problems that will arise. We should therefore get specific about what we care about, and how we'll know whether our agent is sufficiently aligned in the dimensions we care about (ideally) before we release it into the wild.[^3]

By being clear on the product-level implications of different failure modes, we can specify what it means for our agent to be shippable. In the case of my benchmark, one presumably really cares not just about transcription accuracy but also about generally preventing wrong transcription. It's good to be clear about that from the start so whatever unexpected bugs arise will be surfaced by your evals in the dimensions you care about.

Additionally, by understanding how a heuristic diverges from reality, we stand a better chance at identifying root causes of our agents' aberrant behavior. And instead of just throwing the kitchen sink of common techniques at the problem, if we can get an intuition about what's going on by actually looking at *specific examples* in the data, it's often possible to apply a more appropriate solution. Otherwise we resort to band-aid solutions.

In conclusion then, if you want your agent to know when it mishears, make sure you reason through *how* the agent 'knows'. Don't just be like, "was the ASR confident?" Given the audio, transcript, task context, and downstream cost, is there enough evidence to commit this field? And if nothing else, make sure your evals measure what you care about, so the bugs you didn't predict still pop up somewhere you're looking.
